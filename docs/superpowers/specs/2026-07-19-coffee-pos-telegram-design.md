# Дизайн: Кассовая система кофейни на базе Telegram

Дата: 2026-07-19
Статус: утверждён владельцем (устно, по разделам)

## 1. Цель

Кассовая система для одной кофейни (одна точка, один кассир, планшет/моноблок):
приём заказов, оплата (наличные / карта / Kaspi QR), учёт остатков и себестоимости,
смены, отчётность и мониторинг для администратора в реальном времени.

## 2. Ключевые решения (согласованы с владельцем)

| Вопрос | Решение |
|---|---|
| Интерфейс кассира | Telegram Mini App; интерфейс целиком на Python (NiceGUI) |
| Фискализация | Не в первой версии. Печатается нефискальный пред-чек; интеграция с ОФД (Webkassa и т.п.) — отдельный будущий этап |
| Kaspi QR | Полная интеграция с Kaspi Pay API (ИП оформлено, POS-терминал есть): QR на точную сумму, автоподтверждение оплаты. Резерв — ручное подтверждение |
| Принтер чеков | Пока нет. Архитектура закладывает очередь печати; реализация — второй этап. Пока номер заказа показывается на экране |
| Язык серверной части | Python (по решению владельца) |
| Размещение | Этап 1 — локально на компьютере в заведении (публичный HTTPS через туннель cloudflared); при необходимости переезд на VPS без переделок |
| Часовой пояс | Asia/Almaty, валюта — тенге (хранение в тиынах, целые числа) |

## 3. Архитектура

Четыре компонента; этап 1 — всё работает на компьютере в заведении, этап «переезд» —
то же самое на VPS (код не меняется, меняются настройки):

1. **Backend** — Python: FastAPI. Единственный владелец бизнес-логики:
   чеки, оплаты, скидки, склад, смены, отчёты, интеграция Kaspi.
2. **Telegram-бот** — aiogram, в том же процессе (polling — публичный адрес для
   вебхуков бота не нужен). Роли: вход в Mini App, уведомления админу, быстрые
   команды (`/today` и т.п.), диалог «Разрешить скидку?».
3. **Mini App — NiceGUI (чистый Python)**, смонтирован на тот же FastAPI-процесс.
   Весь интерфейс — касса, админ-разделы (меню, тех-карты, склад, отчёты) и
   live-дашборд — пишется на Python; NiceGUI сам генерирует браузерную часть.
   Live-обновление дашборда — штатный механизм NiceGUI (websocket), отдельный
   REST/WebSocket-слой не нужен. Небольшая JS-прослойка одна: чтение и проверка
   Telegram initData для авторизации Mini App. Интерфейс проектируется под палец:
   крупные карточки, минимум касаний (типовой заказ — 2-3 касания).
4. **База данных** — SQLAlchemy: локально SQLite (один файл), на VPS PostgreSQL;
   переключение настройкой. Ночной бэкап + выгрузка копии в облачное хранилище,
   уведомление админу о результате.

Публичный HTTPS для Mini App: локально — туннель cloudflared (постоянная ссылка,
бесплатно); на VPS — обратный прокси Caddy. Ограничение локального этапа: касса,
дашборд и отчёты доступны только пока компьютер в заведении включён и есть интернет.

### Авторизация и роли

- Белый список Telegram-аккаунтов с ролью `cashier` или `admin`.
- Вход в Mini App — по initData Telegram (проверка подписи) + пин-код кассира при
  открытии кассы.
- Права: кассир — продажи, смены, скидка до лимита; админ — всё, включая себестоимость,
  редактирование меню, отчёты, разрешение скидок сверх лимита.

## 4. Модель данных (основные сущности)

- **users** — telegram_id, имя, роль, пин-код (hash), лимит скидки.
- **categories**, **products** — товар: тип (`prepared` | `retail`), категория, цена,
  активность. Для retail — связь со складской позицией.
- **modifier_groups**, **modifiers** — объём S/M/L, молоко, сиропы, добавки; наценка
  (может быть 0); опциональное списание ингредиента.
- **ingredients** — единица измерения, текущий остаток, средневзвешенная себестоимость,
  индивидуальный порог низкого остатка. Штучные товары храним той же таблицей
  (unit = «шт») для единообразия остатков.
- **recipes** (тех-карты) — product (+вариант объёма) → список (ingredient, количество).
- **stock_moves** — журнал всех движений склада: приход, продажа, возврат,
  инвентаризация; ссылка на документ-основание. Остаток = агрегат журнала (кэшируется).
- **purchases** — приход: позиции, количества, суммы; пересчёт средневзвешенной
  себестоимости.
- **shifts** — открытие (кассир, стартовые наличные, время), инкассации, закрытие
  (ожидаемая/фактическая наличность, расхождение).
- **orders**, **order_items** — чек: позиции с зафиксированными ценой и себестоимостью
  на момент продажи, модификаторы, скидки (позиция/чек, % или сумма, кто разрешил),
  статус (`open` → `paid` → `refunded`/`partially_refunded`).
- **payments** — оплаты чека: способ (`cash` | `card` | `kaspi_qr`), сумма, сдача;
  несколько записей на чек = разделение оплаты; для Kaspi — id платежа и статус.
- **refunds** — возвраты: чек/позиции, причина (обязательна), кто оформил.
- **discount_requests** — запросы скидки сверх лимита: статус, ответ админа.
- **print_jobs** — очередь печати (второй этап).
- **notifications_outbox** — очередь уведомлений в Telegram (переживает недоступность API).

Все суммы — в тиынах (integer).

## 5. Ключевые потоки

### Продажа
1. Кассир (смена открыта — иначе касса заблокирована) собирает корзину:
   категории → товар → модификаторы; штучный товар — одним касанием.
2. Скидка: в пределах лимита — сразу; сверх — запрос админу в Telegram
   (кнопки Разрешить/Отклонить), касса ждёт и применяет ответ.
3. Оплата: наличные (ввод полученной суммы → сдача), карта (фиксация факта),
   Kaspi QR (создание платежа через API → QR на экране → автоподтверждение;
   при сбое API — ручное подтверждение с пометкой), либо разделение на два способа.
4. Пробитие чека — одна транзакция БД: заказ + оплаты + списание по тех-картам и
   модификаторам + журнал склада. После коммита: событие на дашборд, проверка порогов
   остатков, постановка чека в очередь печати (когда появится принтер).

### Возврат
Полный или частичный, причина обязательна. Штучные товары возвращаются на склад;
ингредиенты приготовленных напитков по умолчанию не восстанавливаются (настраивается).
Уведомление админу.

### Смена
Открытие (стартовые наличные) → уведомление админу с датой-временем.
Инкассации в течение смены. Закрытие: система считает ожидаемую наличность
(старт + продажи налом − инкассации − возвраты налом), кассир вводит фактическую,
расхождение фиксируется → админу сводка смены.

### Склад
Приход (закупка) → рост остатка, пересчёт себестоимости. Продажа → мгновенное
списание. Инвентаризация → корректировка с причиной. Падение ниже порога →
одно уведомление админу (повтор только после пополнения выше порога).

## 6. Отчёты и мониторинг

- **Дашборд (админ, live)**: выручка/чеки/позиции за сегодня, остатки всех позиций,
  блок «на исходе». Обновление по событию продажи (штатный live-механизм NiceGUI).
- **Отчёты за период**: выручка по способам оплаты; топ товаров; выручка по категориям;
  себестоимость и маржа; смены/кассиры (расхождения, инкассации, возвраты, скидки).
- **Экспорт** — .xlsx, файл отправляется сообщением в Telegram.
- **Команды бота**: `/today` — сводка дня.
- **Уведомления админу**: открытие/закрытие смены, низкий остаток, возврат,
  запрос скидки, инкассация, сбой Kaspi, результат бэкапа.

## 7. Обработка ошибок и надёжность

- Денежные и складские операции — только в транзакциях: чек атомарен.
- Kaspi недоступен → касса работает, ручное подтверждение с пометкой в отчёте.
- Telegram недоступен → уведомления копятся в outbox и досылаются.
- Ночной автоматический бэкап БД + копия в облачное хранилище (обязательно:
  на локальном этапе диск компьютера — единственное место хранения данных).
- Часовой пояс Asia/Almaty во всех отметках времени и отчётах.

## 8. Тестирование

- Юнит-тесты (pytest): расчёт чека (модификаторы, скидки, разделение оплаты, сдача),
  списание по тех-картам, средневзвешенная себестоимость, сверка смены.
- Интеграционные: поток продажи целиком (API + БД), возвраты, пороги остатков.
- Kaspi API — за интерфейсом `PaymentProvider` с мок-реализацией для тестов
  и ручного режима.

## 9. Вне рамок первой версии

- Фискализация (ОФД/Webkassa), физическая печать чеков (архитектурно заложены).
- Экспорт напрямую в Google Sheets (xlsx открывается в Google Таблицах).
- Офлайн-режим, несколько точек продаж, программы лояльности.
