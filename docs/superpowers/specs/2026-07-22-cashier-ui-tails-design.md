# Дизайн: хвосты интерфейса кассира — частичный возврат, разделение оплаты

Дата: 2026-07-22
Статус: утверждён владельцем

## 1. Контекст и область

Первый из пяти подпроектов, на которые разбита оставшаяся работа над приложением
(порядок согласован с владельцем):

1. **Этот подпроект** — частичный возврат по позициям + разделение оплаты в UI.
2. Резервное копирование БД.
3. Этап 4 — отчётность (период, топ товаров, себестоимость/маржа, Excel).
4. Этап 5 — Kaspi Pay API + печать чека.
5. Мелкие технические хвосты безопасности — прицепляются к одному из пунктов 2-4.

Сервисный слой (`sales_service.refund_sale`, `sales_service.create_sale`) уже умеет
и частичный возврат по позициям (`item_qty: dict[int, int]`), и разделение оплаты
(`payments: list[PaymentInput]`) — оба покрыты тестами с этапа 2. В интерфейсе кассира
(`app/ui/cashier.py`) обе возможности не выведены: `refunds_page` предлагает только
«Вернуть полностью», `sale_page` всегда создаёт ровно один `PaymentInput`.

**Скидка в интерфейсе продажи — сознательно исключена владельцем из этого и любого
ближайшего подпроекта.** Сервисный слой её поддерживает и ограничивает по лимиту
кассира; поле ввода в UI не появится, пока не будет отдельного запроса.

## 2. Частичный возврат по позициям

Правки только в `refunds_page` (`app/ui/cashier.py`). Вместо прямого вызова возврата
по клику на заказ — диалог:

- Список позиций текущего заказа: название, `qty − refunded_qty` (сколько ещё можно
  вернуть), числовое поле «Вернуть» (0..остаток, по умолчанию 0).
- Поле «Причина» (обязательно, как и сейчас).
- Кнопка «Оформить возврат»: собирает `item_qty = {item_id: qty для qty > 0}`. Если
  словарь пуст — `ui.notify("Выберите хотя бы одну позицию", color="red")`, без похода
  в сервис. Иначе — `sales_service.refund_sale(session, order_id=..., cashier_id=...,
  reason=..., item_qty=item_qty)`.
- Ошибки сервиса (`ValueError`: неверное количество, заказ уже полностью возвращён,
  нечего возвращать) — уже осмысленный текст, просто прокинуть в `ui.notify`.
- Кнопка «Вернуть полностью» остаётся как отдельный быстрый вариант (не открывает
  диалог, `item_qty=None` — как сейчас), появляется в списке заказов рядом с новой
  кнопкой «Частичный возврат».

## 3. Разделение оплаты на два способа

Правки только в `open_payment` (`app/ui/cashier.py`, экран продажи). В диалоге оплаты:

- Чекбокс «Разделить оплату» (выключен по умолчанию).
- Выключен: поведение как сейчас — один выбор способа, при `cash` — поле «Получено»
  и проверка сдачи.
- Включён: два блока «Способ 1» / «Способ 2» (каждый — свой `ui.select` способа) и
  два числовых поля суммы. Поле суммы способа 2 доступно только для чтения и всегда
  показывает `total − сумма_способа_1` (пересчитывается на каждое изменение первого
  поля) — так деньги гарантированно сходятся, отдельная валидация суммы не нужна.
  Если способ — `cash`, у соответствующего блока дополнительно появляется поле
  «Получено» (сдача считается только для наличного блока, как и сейчас).
- Сборка `payments: list[PaymentInput]` — по одному элементу на активный блок,
  передаётся в `create_sale` без изменений в сервисе.
- Валидация «сумма способа 1 не больше total» — на стороне UI перед отправкой (чтобы
  «остаток» второго способа не ушёл в отрицательный тиын); при нарушении —
  `ui.notify(..., color="red")`, без похода в сервис.

## 4. Тестирование

Бизнес-логика (частичный возврат, разделение оплаты, расчёт сдачи) уже протестирована
в `tests/test_sales_service.py` — новых сервисных тестов не требуется. Обе страницы —
тонкая обвязка вокруг протестированных вызовов, проверяются по образцу существующих
UI-задач: регресс полного набора тестов + ручной рендер страницы (диалоги открываются,
поля считают правильно, вызов сервиса проходит с ожидаемыми аргументами).

## 5. Вне рамок

Скидка в UI, интерактивное одобрение через Telegram, разделение более чем на два
способа оплаты, частичный возврат с изменением причины по каждой позиции отдельно.
