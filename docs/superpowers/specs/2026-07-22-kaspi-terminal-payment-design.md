# Дизайн: реальная оплата через терминал Kaspi Smart POS + настройка

Дата: 2026-07-22
Статус: утверждён владельцем по разделам

## 1. Цель и область

Заменить ручную отметку «оплачено Kaspi QR» на реальное подтверждение оплаты через
терминал Kaspi Smart POS (`192.168.0.100:8080`, локальный HTTP API — документация в
памяти проекта `kaspi-smart-pos-api`). Плюс экран настройки и проверки связи с
терминалом.

**Второй из оставшихся подпроектов** (порядок по факту переставлен по просьбе владельца:
Kaspi раньше бэкапов и отчётности).

**В этап входит:**
- Реальная оплата: кассир выбирает «Kaspi (терминал)» → терминал показывает QR/ждёт
  карту → приложение опрашивает статус → при успехе чек проводится автоматически.
- Экран настройки `/admin/kaspi`: адрес терминала, имя кассы, проверка связи,
  регистрация кассы, статус токена.
- Защита интеграции: работа по токену (register/revoke), как требует документация для
  боевой эксплуатации.

**Вне рамок этого этапа:**
- Возврат через терминал — отдельный следующий подэтап (возвраты редки, флоу сложнее).
- Своя печать чека приложением — нет физического принтера у кофейни. Но чек Kaspi-оплаты
  печатает сам терминал Smart POS (параметр `owncheque=false`, см. раздел 4).
- Kaspi-терминал в разделении оплаты — только как единственный способ на чек (см. ниже).

## 2. Архитектура

Новые модули поверх существующего стека (FastAPI + NiceGUI + aiogram + SQLAlchemy/SQLite,
один процесс, async event loop):

1. **`app/kaspi/client.py`** — тонкий async HTTP-клиент терминала на `httpx.AsyncClient`:
   методы `register`, `revoke`, `deviceinfo`, `payment`, `status`, `actualize`. Только
   ввод-вывод: формирует URL/заголовки, парсит JSON-ответ, поднимает типизированную
   ошибку при `statusCode != 0` или HTTP-ошибке. Никакой бизнес-логики и работы с БД.
   Тестируется подставными ответами.
2. **`app/kaspi/service.py`** — оркестрация поверх клиента и `KaspiSettings`:
   - `check_connection(session) -> DeviceInfo` — `deviceinfo`.
   - `register_cashier(session)` — `register`, сохраняет токены и `terminal_id`.
   - `ensure_token(session)` — обновляет `access_token` через `revoke`, если срок
     близок к истечению.
   - `pay(session, amount_tiyn) -> PaymentResult` — проверяет кратность 100, шлёт
     `payment`, затем опрашивает `status` раз в секунду до финального состояния
     (`success`/`fail`/`unknown`/таймаут ~180 сек), при `unknown` пробует `actualize`.
     Возвращает результат с `status`, `terminal_method`, `transaction_id` или текстом
     ошибки. Async — не блокирует событийный цикл NiceGUI.
3. **`app/models/kaspi.py`** — `KaspiSettings` (одна строка-синглтон): `terminal_url`,
   `cashier_name`, `access_token`, `refresh_token`, `token_expires_at`, `terminal_id`.
   Токены переживают перезапуск приложения.

Kaspi-терминал доступен **только как единственный способ оплаты на чек** — не в
разделении оплаты. Причины: терминал держит одну операцию за раз, а асинхронный
poll внутри диалога разделённой оплаты сильно усложнил бы флоу. Разделение оплаты
остаётся на наличные/карту/ручной Kaspi.

## 3. Модель данных

### Изменения `Payment` (`app/models/payments.py`) — обратно совместимо
Добавить поля (у существующих записей — значения по умолчанию, старое поведение не
ломается):
- `provider: Mapped[str] = mapped_column(default="manual")` — `"manual"` | `"terminal"`.
- `terminal_method: Mapped[str | None] = mapped_column(default=None)` — `"qr"` | `"card"`
  | `"alaqan"` (что вернул терминал; клиент сам выбирает способ на терминале).
- `transaction_id: Mapped[str | None] = mapped_column(default=None)` — `orderNumber`
  (QR/alaqan) или `rrn` (карта). Нужен для будущих возвратов через терминал.

`Payment.method` остаётся как есть. Для терминальной оплаты `method = "kaspi_terminal"`
(новое значение), для ручной отметки-запаса — прежний `"kaspi_qr"`. Так в отчётах
чётко видно, сколько прошло через реальный терминал и сколько отмечено вручную.
`expected_cash_tiyn` не меняется: терминальная оплата не `cash`, в наличные не входит.

### `PaymentInput` (`app/services/pricing.py`)
Добавить те же необязательные поля `provider="manual"`, `terminal_method=None`,
`transaction_id=None`. `create_sale` прокидывает их в строку `Payment` без иной логики.

### `KaspiSettings` (`app/models/kaspi.py`)
```
id: int (всегда 1, синглтон)
terminal_url: str          # напр. "https://192.168.0.100:8080"
cashier_name: str          # имя кассы для register (напр. "Kashier1")
access_token: str | None
refresh_token: str | None
token_expires_at: datetime | None   # tz-aware; из expirationDate ответа
terminal_id: str | None    # из deviceinfo, нужен в заголовке /v2/status
```

## 4. Поток оплаты

1. Кассир: корзина → «Оплата» → способ «Kaspi (терминал)» → «Провести».
2. Проверка суммы: `total_tiyn % 100 == 0`. Иначе — `ui.notify("Kaspi принимает только
   целые тенге", color="red")`, чек не проводится. (Сейчас все цены целые — это защита.)
3. Кнопка «Провести» блокируется; экран показывает «Ожидание оплаты на терминале…»
   со спиннером. `kaspi_service.pay(session, total_tiyn)`:
   - `ensure_token` → `payment?amount=<total_tiyn // 100>&owncheque=false`. `owncheque=false`
     означает «печать чека делает сам терминал» — так как своего принтера у кофейни нет,
     пусть чек печатает встроенный принтер Smart POS. (Параметр стоит перепроверить при
     ручном тесте на реальном устройстве; при желании легко переключить на `true`.)
   - poll `status` раз в 1 сек до финала (таймаут ~180 сек).
4. **`success`** → только теперь `create_sale(..., payments=[PaymentInput(
   method="kaspi_terminal", amount_tiyn=total, provider="terminal",
   terminal_method=<из ответа>, transaction_id=<orderNumber|rrn>)])` → списание склада,
   чек проведён. **Инвариант: чек и списание — только после реального подтверждения.**
5. **`fail`/таймаут** → чек не создаётся, склад не трогается; сообщение об ошибке +
   предложение повторить или переключиться на ручную отметку / другой способ (запасной
   путь — сохраняется прежняя ручная оплата «Kaspi QR»/наличные/карта).
6. **`unknown`** (обрыв связи в момент оплаты) → `actualize`; если снова `unknown` —
   «Статус неизвестен, проверьте на терминале», чек не создаём.

Запасной путь: старый вариант «Kaspi QR» (ручная отметка, `provider="manual"`) остаётся
в списке способов — если терминал недоступен, кофейня не встаёт. Такой платёж помечен
`manual` для отчётности.

## 5. Экран настройки `/admin/kaspi` (только админ)

- Поле «Адрес терминала» (по умолчанию `https://192.168.0.100:8080`) и «Имя кассы».
- **«Проверить связь»** → `check_connection` (`deviceinfo`) → показывает `serialNum` и
  `terminalId` либо текст ошибки. Работает без токена.
- **«Зарегистрировать кассу»** → `register_cashier` → «Подтвердите доступ на экране
  терминала» → сохраняет токены и `terminal_id`, показывает срок действия токена.
- Токен обновляется автоматически (`ensure_token` перед каждой операцией, если срок
  близок).
- Кнопка навигации на `/admin/kaspi` добавляется в `/admin/stock` рядом с «Дашборд».

## 6. Обработка ошибок и надёжность

- HTTPS к терминалу по IP — `verify=False` (документация разрешает доступ по IP, уровень
  защиты тот же; проверка сертификата возможна только по DNS-имени `*.kaspipos.kz`,
  которого в локальной сети нет).
- Любой сетевой сбой/таймаут → чек НЕ создаётся, склад НЕ трогается (оплата гейтит
  продажу — это ядро надёжности этапа).
- `errorText`/`statusCode` терминала логируется; кассиру — короткое понятное сообщение.
- Во время оплаты кнопка «Провести» заблокирована — исключаем запуск второй операции
  (терминал держит одну).
- `ensure_token`: при истечении токена (`HTTP 403`) — один повтор после `revoke`; при
  повторной неудаче — понятная ошибка на экране настройки.

## 7. Тестирование

- `kaspi/client.py` — юнит-тесты с подставными HTTP-ответами (успех и ошибки каждого
  метода: register/revoke/deviceinfo/payment/status/actualize), без реального терминала.
  Клиент принимает базовый URL и (для тестов) инъектируемый `httpx.AsyncClient` или
  transport-мок.
- `kaspi/service.py` — тесты цикла опроса с фейковым клиентом: `wait→wait→success`,
  `wait→fail`, таймаут (превышение числа опросов), `unknown→actualize→fail/success`.
- Конвертация суммы: `total_tiyn // 100`, отказ при `total_tiyn % 100 != 0`.
- `create_sale` с терминальным `PaymentInput` — сохранение `provider`/`terminal_method`/
  `transaction_id` в строке `Payment`; регрессия существующих тестов продаж.
- **Реальный терминал** — только ручная проверка с участием владельца (включить «Защита
  интеграции», подтвердить регистрацию кассы). Автотесты железо не трогают.

## 8. Вне рамок (следующие подэтапы/подпроекты)

- Возврат через терминал (`/v2/refund` тем же способом, что оплата; использует
  сохранённый `transaction_id` + `terminal_method`).
- Печать чека (нужен принтер).
- Kaspi-терминал как одна из ног в разделённой оплате.
- Резервное копирование БД, отчётность за период — отдельные подпроекты по плану.
