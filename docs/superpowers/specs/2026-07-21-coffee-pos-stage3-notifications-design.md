# Дизайн: этап 3 — приход товара, уведомления, live-дашборд

Дата: 2026-07-21
Статус: утверждён владельцем по разделам

## 1. Цель и область

Поверх этапов 1-2 (каталог, склад, продажи, смены, возвраты — в master) добавляем три
куска, отсутствующих в приложении прямо сейчас:

1. **Приход товара через интерфейс** — сейчас `inventory_service.receive_purchase`
   вызывается только из кода; нужна страница ввода.
2. **Уведомления администратору в Telegram** — бот сейчас отвечает только на `/start`,
   никаких событий не шлёт.
3. **Live-дашборд администратора** — выручка/чеки за сегодня, остатки, «на исходе»,
   статус смены; сейчас этого экрана нет.

**Сознательно вне рамок этого этапа** (обсуждено и отложено владельцем):
- Ввод скидки в интерфейсе продажи и её интерактивное одобрение через Telegram —
  откладывается в бэклог следующего UI-этапа. Сервисный слой (`pricing`,
  `discount_within_limit_tiyn`, `create_sale`) уже умеет считать и ограничивать
  скидку — только нет поля ввода и workflow одобрения.
- Отчёты за период, экспорт — этап 4.
- Kaspi API, печать чека — этап 5.
- Уведомление о сбое Kaspi, о результате бэкапа — появятся вместе с этими подсистемами.

## 2. Архитектура

Три независимых куска поверх существующего стека (один Python-процесс: FastAPI +
NiceGUI + aiogram + SQLAlchemy/SQLite):

### Надёжные уведомления
Таблица-очередь `NotificationOutbox`. Бизнес-сервисы (смены, возвраты, склад) только
**записывают** уведомление (`notification_service.enqueue`, один `INSERT`+`commit`,
без сетевого вызова внутри бизнес-транзакции). Фоновая задача внутри процесса бота
(`asyncio`-таск, стартует вместе с `run_bot`) каждые несколько секунд забирает
`pending`-записи и рассылает их всем активным админам; при неудаче запись остаётся
`pending` и уйдёт на следующем тике. Это переживает временную недоступность Telegram,
как требует раздел 7 спецификации.

### Приход товара
Новая страница `/stock/purchase`, доступна и кассиру, и админу (`require_user`).
Использует уже существующий `inventory_service.receive_purchase` — новой бизнес-логики
не требует, только UI-обёртку. Отдельно от `/admin/stock` (только админ), где остаются
тех-карты, пороги, редактирование ингредиентов и себестоимость.

### Live-дашборд
Страница `/admin/dashboard` (`require_admin`). Обновление — периодический опрос БД
(`ui.timer` раз в 3 секунды), без событийной шины. Для транзакционного объёма кофейни
(продажа раз в несколько минут) задержка в пару секунд не имеет значения, а событийная
шина добавила бы код и точки отказа без ощутимой пользы — решение принято явно.

## 3. Модели и уведомления

### `NotificationOutbox` (`app/models/notifications.py`)
```
id: int
kind: str            # "shift_open" | "shift_close" | "collection" | "refund" | "low_stock"
text: str             # готовый текст сообщения
status: str           # "pending" | "sent" | "failed"
created_at: datetime  # tz-aware
sent_at: datetime | None
```
Получатель не хранится в записи: на каждой отправке фоновая задача сама берёт список
активных админов (`User.role == "admin", is_active == True`) и шлёт текст каждому.
Так очередь не завязана на конкретный `telegram_id` и переживает изменения состава
админов между постановкой в очередь и отправкой.

### `notification_service.py`
- `enqueue(session, *, kind, text) -> NotificationOutbox` — только `add`+`commit`.
- `pending(session) -> list[NotificationOutbox]`.
- `mark_sent(session, id)` / `mark_failed(session, id)`.

### Фоновая рассылка (в `app/bot`)
Асинхронный цикл, стартующий рядом с `run_bot`: каждые ~5 секунд читает `pending()`,
для каждой записи шлёт текст всем активным админам через `bot.send_message`, помечает
`sent`/`failed`. Если бот не настроен (`bot_token` не задан) — цикл не запускается,
как и сам `run_bot`.

### Точки вызова `enqueue`
- `shift_service.open_shift` → «Смена открыта: {кассир}, {дата/время}, старт {сумма} тг».
- `shift_service.close_shift` → «Смена закрыта: {кассир}, {дата/время}, ожидалось {X} тг,
  по факту {Y} тг, расхождение {±Z} тг».
- `shift_service.add_collection` → «Инкассация {сумма} тг, смена №{id}, {кассир}».
- `sales_service.refund_sale` → «Возврат {сумма} тг по заказу №{номер}, причина:
  {причина}, {кассир}».
- Проверка порога остатка (новая функция `inventory_service.check_low_stock`,
  вызывается после `apply_move` и после `receive_purchase`): если остаток упал ниже
  `low_stock_threshold` и ранее не был ниже — «Низкий остаток: {ингредиент} —
  {текущий} {ед.} (порог {порог})». Повтор подавляется до тех пор, пока остаток не
  поднимется выше порога (флаг «уже уведомляли» на самом `Ingredient` — простое булево
  поле, сбрасывается при пересечении порога вверх).
- Приход товара сам по себе уведомления не генерирует (рутинная операция) — только
  может сбросить флаг «низкий остаток», если поднял остаток выше порога.

Все точки вызова `enqueue` находятся **внутри** уже существующих атомарных транзакций
(`open_shift`, `close_shift`, `add_collection`, `refund_sale`, `apply_move`) — если
транзакция откатится, уведомление в очередь не попадёт (согласованность с бизнес-данными).

## 4. Приход товара и дашборд

### `/stock/purchase` (`require_user`)
Форма: выбор активной складской позиции → количество → сумма закупки в тенге →
`inventory_service.receive_purchase(session, ingredient_id, qty=..., total_cost_tiyn=...)`.
После сохранения — проверка `check_low_stock` (может снять флаг «низкий остаток»).
Ниже формы — список последних 10 приходов (дата, позиция, количество, сумма) без
себестоимости за единицу и прочей аналитики — это остаётся в `/admin/stock`, видно
только админу.

### `/admin/dashboard` (`require_admin`)
Обновление раз в 3 секунды через `ui.timer`. Блоки:
- **Сегодня**: выручка (`Σ Order.total_tiyn`, где `status != "refunded"` и `created_at`
  в границах текущих суток Asia/Almaty) и число чеков; отдельно — число проданных
  позиций (`Σ OrderItem.qty − refunded_qty` по сегодняшним заказам).
- **Остатки склада**: таблица активных `Ingredient` (название, остаток, единица).
- **На исходе**: подмножество той же таблицы, где `stock_qty < low_stock_threshold`.
- **Смена**: статус (открыта/закрыта), кассир, время открытия — если открыта.

## 5. Обработка ошибок и надёжность

- `enqueue` не должен уметь провалить бизнес-транзакцию: это простой INSERT в ту же
  сессию, без внешних вызовов.
- Фоновая рассылка не блокирует бизнес-операции (отдельный asyncio-таск, как и текущий
  `run_bot`); её сбой (Telegram недоступен) не влияет на кассу.
- Часовой пояс Asia/Almaty при вычислении границ «сегодня» на дашборде — уже принятое
  в спецификации соглашение, здесь применяется впервые в коде (раньше все временные
  метки хранились в UTC, но с ними не сравнивались посуточно).

## 6. Тестирование

- Юнит-тесты `notification_service`: enqueue создаёт запись, `pending()` возвращает
  только `pending`-записи, `mark_sent`/`mark_failed` меняют статус.
- Юнит-тесты точек вызова: `open_shift`/`close_shift`/`add_collection`/`refund_sale`
  кладут в очередь ровно одну запись ожидаемого `kind` с ожидаемым текстом.
- Юнит-тесты `check_low_stock`: падение ниже порога — одна запись в очереди; повторное
  падение без пересечения порога вверх — новой записи нет; после пополнения выше
  порога и повторного падения — снова одна запись.
- Юнит-тесты дашборд-запросов (без UI): функции подсчёта выручки/чеков/позиций за
  сегодня и списка «на исходе» — как чистые функции над сессией, тестируемые без NiceGUI.
- UI-задачи (`/stock/purchase`, `/admin/dashboard`) — по образцу этапа 1-2: ручная
  проверка через рендер страницы + регресс полного набора тестов, отдельных
  UI-юнит-тестов не пишем (страницы — тонкая обвязка вокруг уже протестированных
  сервисов).

## 7. Вне рамок этого этапа (перенесено в бэклог)

- Ввод скидки в UI продажи + интерактивное одобрение через Telegram (кнопки,
  диалог ожидания с опросом статуса) — обсуждено, спроектировано на уровне решения

  одинаково; порог «крупный» не задан.
